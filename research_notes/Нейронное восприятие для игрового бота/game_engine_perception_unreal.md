## 1. Game-AI practice: how shipped games and middleware generate level annotations automatically

### Takeaway
The established technique is geometric, not learned: voxelize collision (the same Recast-style heightfield used for the navmesh), walk navmesh boundary edges, sample candidate trajectories or cover planes against the heightfield, and bake the result as off-mesh links, cover rails or region graphs; runtime "tactical point" queries then score candidates with traces and path tests. By 2025–2026 this is a product feature in middleware (Havok "Automatic Traversal Analysis", Kythera automatic markup) and an experimental built-in in Unreal (jump link generation since UE 5.5).

### Inferences
- Every concrete system found works from the same three inputs: navmesh boundary edges, a voxel heightfield of collision, and agent parameters (radius, height, step height, jump arc). Ledges/drop-offs are navmesh boundary edges with walkable ground below within a depth limit; pits are boundary edges with no ground within the limit; vault/climb candidates are boundary edges with a short obstacle and ground beyond; cover is a boundary edge with solid voxels above a height threshold on the outside. None of this needs rendering or a neural network.
- Stairs and slopes are normally absorbed into the navmesh by `AgentMaxStepHeight` / `AgentMaxSlope` and are not annotated separately; a bot that needs to "know" it is on stairs must derive it from poly normals / height gradients or from collision traces (no shipped system was found that labels stairs explicitly).
- Thin obstacles (poles) and object categories (car, door, chair) are not something the geometric pipelines classify: they output affordances (blocks, coverable, vaultable), not semantic nouns. Semantic nouns in shipped games come from asset-level metadata, not from geometry analysis.
- Doorway/chokepoint detection on a navmesh can reuse the RTS approach: build the medial axis / Voronoi of the walkable area (or use `FindDistanceToWall` samples), mark local minima of clearance as chokepoints, and cut regions there.

## 2. Unreal Engine specifics: what exists out of the box, and what a dedicated server can see

### Takeaway
A UE 5.8 dedicated server has the full Recast navmesh (polygons, wall edges, areas, nav links, nav raycasts), EQS, Smart Objects, State Tree, Mass, gameplay tags, asset user data, physical materials on hit results and all Chaos collision queries, but in a cooked server build static-mesh render LODs are stripped at cook time regardless of "Allow CPU Access", so geometry analysis must use collision and navmesh, not render vertices. Automatic nav link generation (jump down, and up since 5.7) exists since UE 5.5 and is still marked Experimental in 5.8.3; AI Perception covers actor stimuli only and says nothing about level structure.

### Inferences
- In a cooked dedicated-server build the render vertex/index buffers are simply not in the package, so "Allow CPU Access" cannot bring them back there; the flag matters for client/game targets. What the server does have is the `UBodySetup` (simple shapes plus the cooked Chaos triangle mesh for complex collision) and `NavCollision`. All geometry sensing on the server should therefore be collision queries (line traces, sweeps, overlaps, with `bTraceComplex` where needed) plus navmesh queries. Running the uncooked editor binary with `-server` is different: render data is present there, which can hide the problem during development. (Source-read, not runtime-tested.)
- Ledge/drop/pit detection is available today without any new engine feature: `FindEdges` / `GetPolyWallSegments` give navmesh boundary segments; a downward trace or `ProjectPointToNavigation` beyond the edge gives drop height or "no ground" (pit). The experimental generator already does exactly this at build time and writes nav links, so enabling `bGenerateNavLinks` with two or three `NavLinkJumpConfigs` (short drop, long drop, jump-up with negative `JumpMaxDepth`) gives the bot drop/jump affordances as ordinary path links, on client and server alike.
- With a statically built navmesh the generated links are baked into the nav data the server loads; with runtime (dynamic) generation they are produced by the tile generator in whatever process builds tiles, including a server. (Inference from where `dtNavLinkBuilder` sits; not tested.)
- AI Perception answers "which actors do I see/hear", via stimuli sources and line-of-sight traces. It has no notion of stairs, pits, doors-as-geometry or object categories, so it is the wrong layer for structural understanding; it can carry semantic labels only if actors are registered as stimuli and tagged.
- Object nouns (car, door, chair, pole) are best attached at asset level (`UAssetUserData` on the `UStaticMesh`, or a gameplay tag via a data asset / Smart Object definition) and read on the server from `FHitResult.Component -> GetStaticMesh() -> AssetUserData`. Asset user data and tags are ordinary UObject data, not audio-visual data, so they survive the server cook (inference from the strip-flag code; not runtime-tested).

## 3. Automatic semantic labelling inside the editor

### Takeaway
UE 5.8 ships an Experimental, editor-only first-party pipeline that does almost exactly "classify assets with a VLM at edit time": the `SemanticSearch` plugin renders asset thumbnails (static meshes included), sends them to a vision-capable chat model to "generate tags + caption", embeds the caption and builds a hybrid vector + BM25 index, with an OpenAI-compatible endpoint that can be pointed at a local server. No third-party CLIP-based mesh tagging plugin was found; rule-based name/class tools exist.

### Inferences
- The cheapest route to "the bot knows this mesh is a car / chair / door / pole" is edit-time labelling of the few thousand distinct static-mesh assets, not run-time recognition: label once per asset, store the label on the asset (`UAssetUserData` or a tag table keyed by asset path), and read it on the server from the hit component. Instances inherit the label for free and nothing runs at game time.
- Three labelling sources can be stacked, cheapest first: (1) asset name and folder heuristics via Asset Registry / Editor Utility Python; (2) a VLM caption+tags pass over thumbnails, which Epic's own `SemanticSearch` now demonstrates inside the editor and which can run against a local OpenAI-compatible server; (3) geometric descriptors from collision (bounding-box aspect ratio, height, footprint) to disambiguate poles, railings and thin obstacles that names miss.
- `SemanticSearch` is designed for search, not for writing gameplay metadata; using its captions as bot labels would need a small editor script that reads its per-asset output and writes tags. It is "very early work in progress" and its defaults send thumbnails to a third-party API, which matters for unreleased content.

### Gaps
- When `SemanticSearch` and the Toolsets first appeared (5.7 or 5.8) was not determined; they are confirmed present only in 5.8.3 source.
- Where `SemanticSearch` persists generated tags/captions beyond DDC, and whether they are exposed as Asset Registry tags, was not checked.
- No published write-up was found of a studio classifying static meshes with CLIP-like models at edit time for AI purposes; absence in two searches is weak evidence, not proof of absence.
- PCG-based attribute tagging and Epic's prose docs for Asset Registry metadata were not researched.

## 4. Running neural networks inside Unreal: NNE, its runtimes, dedicated server, Learning Agents, alternatives

### Takeaway
NNE is Beta in UE 5.8 and `NNERuntimeORTCpu` is a plain CPU path with no rendering dependency in its code: UE 5.8.3 bundles ONNX Runtime 1.24.1 (C API version 24), loads it by absolute path, registers the CPU runtime unconditionally, and defaults non-editor targets to single-threaded execution on the calling thread. Nothing in the source gates it off on a dedicated server (source-read, not runtime-tested). The engine's ORT is four minor versions behind the team's 1.28, and a second same-named `onnxruntime.dll` in the process is a real hazard unless it is loaded by full path or renamed.

### Cited Findings
Status and API:
- Epic's UE 5.8 overview calls NNE a Beta feature ("Learn to use this Beta feature, but use caution when shipping with it") and names three interfaces: `INNERuntimeCPU`, `INNERuntimeGPU`, `INNERuntimeRDG`; "Not all runtimes are available on all platforms, even when the corresponding plugin is enabled" — [Epic docs: Neural Network Engine overview (5.8)](https://dev.epicgames.com/documentation/en-us/unreal-engine/neural-network-engine-overview-in-unreal-engine)
- CPU interface "covers all use cases where inference should happen on the CPU" and suits cases "when there is no budget on the GPU"; CPU models can run on the game thread, in an async task or on another thread "as long as the caller takes care of thread safety and memory lifetime"; GPU inference "will compete with the rendering pipeline for GPU resources" and typically serves editor-only use cases; RDG is for networks that consume/produce frame resources — [Epic docs: NNE overview (5.8)](https://dev.epicgames.com/documentation/en-us/unreal-engine/neural-network-engine-overview-in-unreal-engine)
- Importing an `.onnx` file creates a `UNNEModelData` asset; target runtimes can be enabled/disabled per asset, and "Removing unwanted runtimes increases packaging speed and decreases package size" — [Epic docs: NNE overview (5.8)](https://dev.epicgames.com/documentation/en-us/unreal-engine/neural-network-engine-overview-in-unreal-engine)
- In 5.8.3 the NNE core is an engine runtime module (`Engine/Source/Runtime/NNE`), with interface headers for CPU, GPU, RDG and also NPU (`NNERuntimeNPU.h`) — [UE 5.8.3 src: Runtime/NNE/Public](https://github.com/EpicGames/UnrealEngine/tree/5.8/Engine/Source/Runtime/NNE/Public)
- `IModelInstanceRunSync::RunSync` "will block the calling thread until the inference is complete"; "Clients can call this function from an async task but must make sure the memory remains valid"; `SetInputTensorShapes` is mandatory before running and "potentially expensive" — [UE 5.8.3 src: NNERuntimeRunSync.h](https://github.com/EpicGames/UnrealEngine/blob/5.8/Engine/Source/Runtime/NNE/Public/NNERuntimeRunSync.h)
- At cook time `UNNEModelData` drops the raw file data and stores per-runtime model data for each target runtime; an empty `TargetRuntimes` list means "all currently registered ones" — [UE 5.8.3 src: NNEModelData.cpp](https://github.com/EpicGames/UnrealEngine/blob/5.8/Engine/Source/Runtime/NNE/Private/NNEModelData.cpp)

### Inferences
- Dedicated server, CPU only: by code reading `NNERuntimeORTCpu` should work in a UE 5.8 Windows or Linux dedicated server. The plugin module type loads on all targets, the platform list includes Linux and LinuxArm64, the CPU runtime is registered without any render check, and the Dml path degrades to "not available" without a D3D12 RHI. This was not run; the first thing to verify on a packaged Lyra server is the log lines `MakeRuntimeORTDml:` and whether `UE::NNE::GetRuntime<INNERuntimeCPU>(TEXT("NNERuntimeORTCpu"))` returns a valid runtime.
- Because `NNEDenoiser` is on by default and its modules are `Runtime` type, `NNERuntimeORT` (and therefore `onnxruntime.dll` 1.24.1, plus `DirectML.dll` on Windows) is probably already loaded in the team's client, and by descriptor semantics in the server too, even though the project never asked for NNE. If the project does not use the path tracer, disabling `NNEDenoiser` removes that load; if the bot uses `NNERuntimeORTCpu`, enable `NNERuntimeORT` explicitly instead.
- Threading on a server: the shipped default (intra-op 1, inter-op 1, no ORT thread pool) means `RunSync` costs exactly one core for its duration on whatever thread calls it. That is the right default for a server with many bots: call from a task-graph/background task, batch several bots' inputs into one call if the model has a batch dimension, and never call per-bot per-frame on the game thread. Raising intra-op threads creates an ORT-owned pool that competes with the engine's task graph.
- Version mismatch: the engine's ORT (1.24.1, API 24) is older than the team's helper-process ORT (1.28). A model exported for 1.28 runs under NNE only if its opset and operators are supported by 1.24.1; exporting with a conservative opset (for example 17–21) sidesteps this. The exact maximum opset of 1.24.1 was not confirmed (see Gaps).
- Two ORT copies in one process: Epic binds to its own copy through the handle returned by an absolute-path load, so the engine side is robust. The danger is on the other side: any module that imports or delay-loads `onnxruntime.dll` by bare name after the engine's copy is loaded gets the engine's 1.24.1 from the loaded-module list, and a request for API version 28 from a 1.24 library fails. Safe patterns, mirroring Epic's own: (a) keep the 1.28 runtime in the separate helper process, as now; (b) if it must be in-process, load it by absolute path, resolve `OrtGetApiBase` from that handle with `ORT_API_MANUAL_INIT`, and wrap the C++ API in a different inline namespace; or (c) rename the DLL. Also note the provider DLLs: dependencies of a full-path-loaded DLL are still searched by module name. (Reasoning from the two cited sources; not tested.)
- For small policy-style networks (MLPs on ray/height features) `NNERuntimeBasicCpu` avoids ORT entirely, but it is Experimental, takes its own `ubnne` format rather than ONNX, and is designed around Learning Agents' Python export.
- `NNERuntimeRDG` and the Dml runtime are irrelevant for a no-render server. `NNERuntimeIREE` is the one to watch for CPU inference without a third-party DLL ("compiles neural networks directly to game code"), but its server suitability was not examined.
- Learning Agents targets learned control policies (RL / imitation), not perception labelling; it is still Experimental in 5.8.3. Its lidar-style observations are the engine-native pattern for feeding geometry to a network.

### Gaps
- Which ONNX Runtime version each of UE 5.4, 5.5, 5.6 and 5.7 bundles was not verified. The wrapper header's own example namespace (`Ort011401`) suggests an earlier engine version shipped 1.14.1, but that is a hint, not a finding.
- Maximum ONNX opset supported by ORT 1.24.1: the official compatibility table as fetched listed rows only up to ORT 1.20 (opset 21). The 1.24.1 notes say ONNX 1.20.1; the corresponding opset number was not confirmed from a fetched source.
- NNE status per version (Experimental in 5.2–5.3, Beta later) and when each runtime appeared were not verified for 5.4–5.7.
- No runtime measurement of NNE CPU latency on a dedicated server; no Epic latency guidance beyond the threading tooltips was found.
- No documented report was found of an actual crash from two `onnxruntime.dll` copies inside Unreal; the hazard is derived from loader rules. The often-repeated claim that Windows may pick up a system copy of `onnxruntime.dll` from System32 was not sourced here.
- Alternatives named in the brief (libtorch, TensorFlow Lite, ncnn inside Unreal) were not researched; no sources retrieved.
- The `INNERuntimeNPU` interface exists in 5.8.3 source but is absent from the 5.8 overview page; which runtime implements it was not checked.

## 5. Synthetic data from a game engine, and how well it transfers

### Takeaway
Tooling to pull labelled images, depth, segmentation and geometry out of Unreal is mature (UnrealCV / UnrealZoo, SPEAR, Colosseum, plus Isaac Sim Replicator as the Omniverse analogue). The transfer evidence says: scale and diversity of procedural scenes matter more than photorealism, coverage gaps hurt, and geometry-only inputs (height samples, occupancy) trained in simulation transfer well when the deployment sensor matches. For this team the deployment domain is the engine itself, so the sensor gap is zero and only the content-distribution gap remains.

### Cited Findings
Tools:
- UnrealZoo (Zhong et al., arXiv Dec 2024, ICCV 2025): over 100 photorealistic UE worlds with playable humans, animals, robots and vehicles; extends UnrealCV with "optimized APIs and tools for data collection, environment augmentation, distributed training, and benchmarking"; reports that environmental diversity gives substantial benefits for generalizable RL agents and that current embodied agents still struggle in open-world settings — [UnrealZoo, arXiv 2412.20977](https://arxiv.org/abs/2412.20977)
- SPEAR (arXiv July 2026): a Python library that "can connect to, and programmatically control, any Unreal Engine application through a modular plugin architecture", exposing over 14K UE functions to Python; ground truth includes non-diffuse intrinsic image decomposition, material IDs and physically based shading parameters — [SPEAR, arXiv 2607.06701](https://arxiv.org/abs/2607.06701)
- SegGen (2025): a UE5 pipeline that procedurally generates labelled environments and captures RGB, depth and pixel-perfect semantic segmentation from a drone; proof of concept of 1169 samples, two modalities, seven classes — [SegGen, Sensors / PMC](https://www.ncbi.nlm.nih.gov/pmc/articles/PMC12431427/)
- Colosseum: community successor of AirSim (Microsoft shut AirSim down in July 2022), maintained by Codex Laboratories as an Unreal plugin; main branch targets UE 5.2, with reports of 5.3/5.4 support — [CodexLabsLLC/Colosseum](https://github.com/CodexLabsLLC/Colosseum)
- Isaac Sim Replicator (the non-Unreal analogue): annotators attach to render products and include 2D tight/loose and 3D bounding boxes (per-object `semanticId`, box corners, `occlusionRatio`), semantic and instance segmentation, and point clouds; prims must carry semantic labels first (Semantics Schema Editor or script) — [Isaac Sim Replicator overview](https://docs.isaacsim.omniverse.nvidia.com/4.5.0/replicator_tutorials/tutorial_replicator_overview.html); [Isaac sensor extension docs](https://docs.isaacsim.omniverse.nvidia.com/4.2.0/py/source/extensions/omni.isaac.sensor/docs/index.html)

Transfer evidence, images:
- ProcTHOR (NeurIPS 2022): agents trained only on RGB in 10K procedurally generated houses reached state of the art on six embodied-AI benchmarks, with "strong 0-shot results" that often beat prior systems trained on the benchmark's own data; performance rises with the number of training houses (10, 100, 1K, 10K). These are simulator benchmarks, not real-robot tests; per-benchmark numbers not checked against the full paper — [ProcTHOR, arXiv 2206.06994](https://arxiv.org/abs/2206.06994v1); [project page](https://procthor.allenai.org/)
- Infinigen (CVPR 2023): a stereo model trained entirely on Infinigen's procedural natural scenes performs well zero-shot on real natural-scene stereo images, but is worse on Middlebury, which is mostly indoor man-made objects (29.7% error vs 25.0% for a SceneFlow-trained model; numbers from a search extract of the supplement) — [Infinigen CVPR 2023 supplemental](https://openaccess.thecvf.com/content/CVPR2023/supplemental/Raistrick_Infinite_Photorealistic_Worlds_CVPR_2023_supplemental.pdf)
- Infinigen-Stereo (2025): a procedural generator tuned for zero-shot stereo; "models trained only on data from our system outperform robust baselines trained on a combination of existing synthetic datasets" — [What Makes Good Synthetic Training Data for Zero-Shot Stereo Matching?, arXiv 2504.16930](https://arxiv.org/abs/2504.16930v1)

Transfer evidence, geometry instead of images:
- Point clouds, synthetic CAD to real scans: models trained on ModelNet40 CAD shapes and tested on the 11 shared classes of ScanObjectNN real scans all scored below 50% accuracy; causes named are partial/incomplete objects, surface noise and inaccurate boundaries — [Uy et al., ICCV 2019, arXiv 1908.04616](https://arxiv.org/pdf/1908.04616)
- A later sim-to-real paper reports DGCNN trained on ModelNet at 49.3% on ScanObjectNN (background removed), dropping to 42.4% and 36.8% on perturbed variants (numbers from a search extract, not checked against the table) — [Sim2Real 3D object classification, arXiv 2103.06134](https://arxiv.org/pdf/2103.06134)
- Height samples for legged robots: Miki et al. (2022) trained a perceptive locomotion controller for ANYmal in simulation and deployed it outdoors, including a 2.2 km mountain hike with zero falls (summary source) — [Learning robust perceptive locomotion for quadrupedal robots in the wild, arXiv 2201.08117](https://arxiv.org/abs/2201.08117)
- Long et al. (2024): "train the policy using ground-truth obstacle heights surrounding the robot in simulation ... and perform inference with heights sampled from the constructed elevation map", deployable zero-shot — [Learning Humanoid Locomotion with Perceptive Internal Model, arXiv 2411.14386](https://arxiv.org/abs/2411.14386v1)
- In-engine geometry as the training input for game agents: Ubisoft's navigation agent perceives a 3D occupancy map from box casts ("can be generated and cached offline") plus a 2D depth map obtained "by casting RayCasts" instead of a rendering camera — [Deep RL for Navigation in AAA Video Games, arXiv 2011.04764](https://arxiv.org/abs/2011.04764v2)

### Inferences
- The classic geometric sim-to-real gap (clean CAD vs noisy partial scans, below 50% accuracy) does not apply here: training samples and inference samples would both be produced by the same engine collision queries. What remains is a content gap between whatever geometry the training set covers and the hand-authored levels the bot meets. ProcTHOR and Infinigen both say the remedy is breadth of generated content and explicit coverage of the target category mix (Infinigen's natural-scene model degrading on indoor Middlebury is the warning).
- Labels for structure are free in-engine and exact: a pit, ledge, stair run, slope, drop height or door opening can be computed analytically from collision and navmesh at data-generation time (the geometric methods of section 1 are the label function), then a network is trained to reproduce those labels from a cheap local sensor (a ray fan, a height patch, a small occupancy grid). This distils an expensive offline analysis into a fast run-time model and gives a parity test for free.
- Labels for object nouns are also free if assets are tagged (section 3): every hit component yields its asset label, so a per-ray or per-voxel semantic channel can be generated without rendering, on a dedicated server or in a commandlet.
- Because the server has no render data, a perception model that must run server-side should take collision-derived inputs (height field around the agent, ray-cast depth fan, voxel occupancy with a semantic channel). Image-based tools (UnrealCV, SPEAR, Replicator) are relevant only for client-side or offline models.
- Data generation does not need the external research toolkits at all for this case: an Editor commandlet or a headless server that walks levels and records `(local geometry sample, analytic label)` pairs is enough. The toolkits become useful if the team later wants rendered images.

### Gaps
- No paper was found that trains a classifier for game-level structural features (stairs, ledges, pits) from engine height fields or voxel grids and reports accuracy; the evidence above is by analogy from navigation policies and robotics.
- Habitat, Objaverse rendering pipelines and domain-randomization specifics of Replicator were not researched (search returned nothing usable in this pass).
- UnrealCV's own documentation was not fetched; it is covered only through UnrealZoo.
- Whether UnrealZoo / SPEAR support UE 5.8 specifically was not checked.

## 6. Machine-learned level understanding for game bots as of 2026

### Takeaway
Published learned systems for moving through game levels do not perceive pixels: they consume engine geometry queries (ray-cast distance fans with a semantic class per ray, cached 3D occupancy grids, ray-cast depth maps) and are used for navigation and automated testing, mostly as research or internal tools. Pixel-input agents exist as research (CS:GO behavioural cloning). The 2025–2026 language-driven companions (Tencent F.A.C.U.L., NVIDIA ACE / PUBG Ally) are announced with "scene recognition" or multimodal perception, but no source found discloses how they sense level geometry. No shipped example was found of a learned geometry-perception model running on a dedicated server to replace designer markup.

### Cited Findings
- Ubisoft La Forge (Alonso, Peter, Goumard, Romoff; IJCAI 2021): deep RL to navigate 3D maps "using any navigation ability" instead of a navmesh, motivated by jump pads, double jumps, grappling hooks and jetpacks making navmesh links intractable; local perception = 3D occupancy map from box casts (generated and cached offline) + 2D depth map from ray casts, each through its own feature extractor (3D convs, 2D convs), merged with goal-relative position and velocity, then an LSTM feeding policy and critic; at least 90% success in point-to-point navigation on maps "an order of magnitude larger" than typical deep-RL maps; tested in Unity and run inside the engine of Hyper Scape — [arXiv 2011.04764](https://arxiv.org/abs/2011.04764v2); [Ubisoft La Forge blog](https://ubisoft.com/en-us/studio/laforge/news/6bRtGllmfhuDqTHRS6KVLj/deep-reinforcement-learning-for-navigation-in-aaa-video-games); [IJCAI 2021 proceedings](https://www.ijcai.org/proceedings/2021/294)
- The GDC 2021 Machine Learning Summit talk on this work says it gives "examples of successful integrations in Ubisoft games" without the retrieved abstract naming them; a January 2024 CEDEC recap presents the same line of work (bots navigating with player controls via deep RL) — [GDC Vault: ML Summit, Deep RL for navigation](https://gdcvault.com/play/1027382/Machine-Learning-Summit-Deep-Reinforcement); [Ubisoft La Forge CEDEC recap](https://ubisoft.com/en-us/studio/laforge/news/6cY2C5m3H5RkFAAsiPYpRh/talk-at-cedec-joshua-romoff-talks-about-how-we-can-build-efficient-player-bots-using-deep-reinforcement-learning)

### Inferences
- The input representations that industry labs converged on (12–24 semantic rays; a cached occupancy grid; a ray-cast depth map) are exactly what a no-render dedicated server can produce from collision. They are small enough for CPU inference: tens of floats for ray fans, a few thousand cells for local occupancy. That is the practical template for a server-side perception model.
- "Semantic ray" inputs presuppose that every collider already knows its class. In other words the learned systems sit on top of asset tagging; they do not replace it. This matches the split recommended in sections 2 and 3: nouns from asset metadata, affordances from geometry.
- Marketing descriptions of F.A.C.U.L. ("recognizes 17,000 in-game items") and ACE ("perceive their environment") are consistent with perception through named game-state entities rather than learned 3D understanding, but neither source says so explicitly; treat this as an interpretation.
- A learned model earns its place where analytic rules are brittle or too slow at run time: fused judgments like "is this gap jumpable at my current speed", "is this a stair run or a pile of debris", "which side of this object gives cover". For the plain cases (drop height, pit, slope angle) the analytic navmesh/collision tests of section 1 are cheaper, exact and need no model.

- Sony AI (GT Sophy), NetEase, inworld and any Tencent technical paper were not researched or returned nothing citable; no claims are made about their inputs.
- Which Ubisoft games integrated the RL navigation, and whether any shipped to players, is not stated in retrieved sources.
- Architecture details of F.A.C.U.L. and ACE perception (game-state API vs vision model vs both) are not public in the retrieved sources; the GDC 2025 slides were not read.
- No source found for learned traversability or level-structure classification deployed in a shipped game on a dedicated server; this may reflect non-publication rather than non-existence.
